## Never choose your own migration filename

The Lead allocates the timestamp. Filenames order the apply sequence, policies are `PERMISSIVE` and therefore OR'd together, and an out-of-order pair can **silently widen access**. If you were not given a slot, ask for one.

## The permission model is non-negotiable

Four roles, `viewer → editor → admin → owner`. Reproduce the matrices from Part II exactly; never invent a role, a boolean permission column, or a fifth capability tier.

Owner immutability (I1–I6) is enforced **in the database**, against every writer including `service_role`:

- The Owner's membership row cannot be deleted or demoted by any actor, including the Owner.
- An admin has no path to an Owner-held row at all — not by RPC, not by a `boards` update.
- `boards.owner_id` and the `owner` row in `board_members` never drift apart.
- Ownership transfer is not a membership operation and does not exist yet.

`board_members` has **no client INSERT/UPDATE/DELETE policy and must never get one.** Every membership mutation goes through a `SECURITY DEFINER` RPC that performs its own authorization check.

## House rules for the SQL itself

- `SECURITY DEFINER` functions: `stable` where possible, `set search_path = ''`, every reference schema-qualified, `revoke all from public, anon`, `grant execute to authenticated` (and `service_role` only when needed).
- Membership-sensitive policies call the helpers (`is_board_member`, `board_role`, `accessible_board_ids`). **Never sub-select `board_members` inside a policy** — that recurses and returns a hard 500.
- Spell out all four verbs separately rather than one `FOR ALL`. An upsert is checked against INSERT `WITH CHECK`, UPDATE `USING` **and** UPDATE `WITH CHECK`; a missing UPDATE policy drops writes silently instead of erroring.
- UPDATE policies carry both `USING` and `WITH CHECK`. `USING` alone lets a row be moved out of its board.
- Every `SECURITY DEFINER` function checks the caller's role itself — definer rights bypass RLS.
- Invariants that must hold for *every* writer go in triggers or constraints, not in one function's body. `todos_assign_board_key` is the precedent.

## Every migration file you write must contain

1. The task ID, risk label, and **Tier A or Tier B** classification (Rule 6 in the plan).
2. Preconditions — what must already be applied.
3. **The exact prior definition, captured verbatim in a comment.** For Tier A this *is* the rollback; without it the reversal is reconstruction from memory.
4. The SQL, commented with the reasoning, not the mechanics.
5. A rollback section: the forward-fix SQL, ready to copy-paste into a new migration.
6. A verification section: preflight checks, then REST-level checks per role after applying. **An empty array from a denied read is a pass; a UI screenshot is not evidence.**

## How to report back

Explain before you hand over code:

1. What you are changing and why.
2. What existing behaviour it affects.
3. The trade-offs you weighed, and anything you decided that the plan did not already settle.
4. What the Lead must run to apply and verify it — as instructions for them, since you cannot run it.

Flag anything ambiguous rather than resolving it silently. A schema decision made quietly is one the Lead cannot explain later, which defeats the point of the work.

Never commit, never push. Never claim something was verified when it was not.
