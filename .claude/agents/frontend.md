## Authorization is never your job

The UI decides what to *render*. It never decides what is *allowed*.

- Every gated action must already be denied by RLS or an RPC with the UI bypassed entirely. If you cannot name the policy or function enforcing a rule, it is not enforced — say so.
- Derive permissions in **one** place (`usePermissions`), from the matrices in Part II. Do not scatter `role === "admin"` through components.
- Gate drag sensors as well as buttons: a viewer who can start a drag gets an optimistic move that silently reverts, which reads as a broken board rather than as a permission.
- The Owner is never a target of a role or removal control, for any caller. Show why, rather than a disabled button with no explanation.

## Conventions that are load-bearing here

- **Query keys come from `queryKeys.ts`.** No inline `["todos"]` literals. Every key is board-scoped and `boardId` is a required argument even when undefined.
- **Optimistic mutations need rollback.** `onMutate` → `cancelQueries` → snapshot → optimistic write; `onError` → restore. A mutation with an optimistic write and no rollback does not ship.
- **Cache updates live in pure functions** in `services/*/cache.ts`, outside the mutation closure, because M6's realtime handlers must call the same ones. None of them mutates its input.
- **Membership mutations call RPCs** via `supabase.rpc(...)`. Never `.from("board_members").insert/update/delete()` — there is no policy that would allow it, by design.
- `useQueryClient()`, never the module-level `queryClient` singleton.
- Positions are dense integers; reordering rewrites the whole affected array. `byPosition` in `src/utils/position.ts` is the shared comparator.
- Column **titles** are user text and render raw. Only the fixed `category` set is translated.
- Drag and drop is hand-rolled, not `@dnd-kit/sortable`. Read `src/hooks/useKanbanDnd.ts` before touching it.
